# Simple workflow

Use this workflow only with `--simple`. The agent receiving the skill invocation performs the entire run directly in the current session. Start with parsing and preflight immediately; do not spawn a root wrapper, coordinator, implementation agent, or any other subagent, including to invoke this skill. This replaces the standard workflow's mandatory delegation, role boundaries, model selection, and handoff requirements.

Read [workflow.md](workflow.md) for its workspace, validation, delivery, and retry safeguards. Perform every role's work yourself wherever it calls for delegation, applying the substitutions in this file wherever they conflict. The current session still performs all repository work in dedicated Git worktrees.

1. Parse scope, delivery mode, `--model`, and `--effort` as specified in [the skill](../SKILL.md), rejecting invalid flags before GitHub access. Perform the standard workflow's preflight and inventory checks yourself, including determining repository-specific verification requirements. Collect the complete raw inventory, including labels and dependencies. Apply the human-involvement label rule, report skipped issues and labels, and keep unresolved skipped prerequisites as blockers.
2. Assess dependencies, eligibility, grouping, and order from the inventory and repository evidence. Apply the standard workflow's dependency ordering and grouping rules; never group a skipped issue. In single-issue mode do not group or implement dependencies. Process efforts sequentially, waiting for prerequisites to reach the applicable delivery boundary; unrelated skipped or blocked issues do not stop eligible work. Use the inventory snapshot as the eligibility decision and report its potential staleness.
3. For each executable issue or approved group, select its dedicated worktree, run the baseline, research when useful, diagnose bugs, plan, implement, review, and validate yourself in this session. Use the issue data, repository instructions, verification requirements, and prior effort results directly; no delegation or handoff files are needed.
4. Follow the standard workflow's validation, delivery, CI, and reporting safeguards for the selected mode. Preserve pre-existing work and honor required checks and branch protections. Apply [Correction cycles and tooling recovery](workflow.md#correction-cycles-and-tooling-recovery): diagnose and fix failures yourself, grouping repairs into at most five substantive cycles across local checks and CI. Exercise required tooling before implementation; unexpected tooling failures get one grouped recovery round excluded from that count. Do not split routine tooling fixes into separate heavyweight cycles. Stop and report evidence if the substantive limit or tooling-recovery allowance is exhausted with failures unresolved. Do not bypass checks or guess at an unknown root cause. Use a fresh branch and dedicated worktree per effort in default and `--no-pr` modes; `--no-commit` reuses only its dedicated run worktree. All preflight, edits, and validation also run in dedicated worktrees. In default mode create a PR and rebase-merge only after required checks pass, then verify issue closure and linear history. With `--no-pr`, commit, rebase onto the latest local `main`, resolve conflicts yourself, rerun applicable checks, fast-forward `main` with `--ff-only`, and unregister and fully delete any workflow-created worktrees along with all contents on disk once merged into `main` (retaining worktrees in default and `--no-commit` modes, and preserving any unintegrated worktree from a failed effort). Acquire the repository-wide integration lock directly to serialize integration across concurrent runs; no separate coordinator grants an integration turn. Never create merge commits on `main`. Reduced modes perform no GitHub writes; if an attempted effort cannot complete, stop further implementation and preserve unfinished changes.
5. Record each effort's outcome and return the standard workflow's final report, including skipped and blocked issues, the current session's model and effort when known, verification, and delivery outcomes. Do not claim success for blocked or unchecked work.

Keep the current session's model, reasoning effort, and execution mode. Subagent model selection (including issue labels), fast-mode propagation, and thread-exhaustion rules do not apply because no subagents are spawned. Validate `--model` and `--effort` syntax when supplied, but report that these subagent settings do not reconfigure the current session; never spawn an agent or switch sessions to satisfy them. Delivery boundaries remain in force. If you cannot complete an effort, report the blocker and preserve its worktree.
